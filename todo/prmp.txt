============== THE LAST ANALYSES HOW BOT TAKE DECISION AFTER COMPLETED THE 7 Phase ==============
Short answers, based on the current code.

**1. Same as realmahjongg.com?** I can't see their code, so I can't promise "exactly the same". What our engine does: it follows the NMJL card through our JSON. After Steps 6, 7 and 7B, wins are checked strictly (suits, exposures, jokers), and both benchmarks show 0 illegal wins.

**2. Does the bot think like a human?** Partly.
- **Human-like:** it sees only public information, aims at a few card hands, drops hands that become impossible, and defends late in the game.
- **Not human-like:** every level waits the same fixed 1 second per turn ([service.ts:2126](apps/app/src/graphql/business-app/game-engine/service.ts#L2126)), and it doesn't read opponents' exposures to guess their hands.

**3. How does it pick and follow a winning hand?** After the deal it scores every card hand by how many tiles it still needs, counting tiles already discarded as gone. It keeps the closest few, then narrows them after the Charleston and after each exposure.

**4. Pung / Kong / Quint?** It claims a discard only if the new exposure fits one of its target hands **and** doesn't move it further from Mah Jongg. It tries the largest group first (sextet → quint → kong → pung).

**5. Several possible winning hands?** It keeps several targets open while they're all reachable, and drops them one by one as exposures and dead tiles rule them out. When it wins, any matching hand counts; it doesn't aim for the highest-value hand.

**6. Discard?** It scores each tile in its hand and discards the one its target hands need least. Jokers and tiles it needs are protected. Late in the game the HARD bot prefers "safe" tiles that others have already discarded.

**7. Different per level?** Only partly.

| Area | Same for all levels? |
|---|---|
| How many target hands it keeps (EASY 3→2→1, NORMAL 6→3→2, HARD 10→5→2) | Differs |
| Discard choice | Differs: EASY and NORMAL sometimes pick the 2nd-best tile |
| Late-game defense | Differs: HARD strong, NORMAL light, EASY none |
| Claiming pung/kong/quint | **Same for all** |
| Think time | **Same for all** (1 second) |
| Profile settings `claimAggression`, `errorRate`, `defenseWeight`, `charlestonQuality`, `thinkTimeMin/Max`, … | **Defined but never used** |

**Joker-swap signal for the UI:** you're right, something is missing. The engine sets `play.last_joker_exchange`, but:
- it keeps only the **last** swap, so if the bot makes 2 swaps in one turn, the UI sees only 1;
- it is **never cleared**, so the UI may replay an old swap on later updates;
- it doesn't say **which rack or which exposure** received the tile.

## Types (in type.ts; reuse existing `Assignment`)
Tile maps use `Record<string, number>` keyed by TileKey strings, matching
`GroupMatchDetails.neededTiles`. Do NOT use `Record<TileKey, number>`: TileKey has literal
members, which would make every one of them a required key.
```ts
export type BotPlanEvent =
  'DEAL' | 'CHARLESTON_RECEIVE' | 'CHARLESTON_DONE' | 'EXPOSURE' | 'TURN' | 'REPLAN';

export type BotPlanStage = 'AFTER_DEAL' | 'AFTER_CHARLESTON' | 'AFTER_EXPOSURE';

export interface BotTargetHypothesis {
  key: string;                         // `${ruleId}|${stable JSON of assignment, keys sorted}|${variantIndex ?? '-'}`
  ruleId: string;
  assignment: Assignment;
  variantIndex: number | null;         // index into groupsAnyOf; null when the rule uses `groups`
  rawDistance: number;
  scarcityPenalty: number;
  isFeasible: boolean;
  isConcealed: boolean;
  neededTiles: Record<string, number>; // tiles still MISSING
  usedTiles: Record<string, number>;   // tiles ALREADY IN THE RACK (hand + exposures) this hand uses; jokers under 'J'
  weight: number;
}

export interface BotPlan {
  hypotheses: BotTargetHypothesis[];
  version: number;                     // set by saveBotPlan: previous saved version + 1
  lastEvent: BotPlanEvent;
}

export type BotPlanStore = Record<number, Record<number, BotPlan>>; // seatId -> rackId -> plan
```
Critical definition: keep and discard decisions use `usedTiles`, NEVER `neededTiles`.
A tile that already completes a group is in `usedTiles` and is not in `neededTiles`.
